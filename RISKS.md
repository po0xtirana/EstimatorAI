# BidPilot Assumptions & Risk Register

| ID | Decision / assumption | Why | Confidence | What breaks if wrong | Status |
|---|---|---|---|---|---|
| R-001 | Start with CanadaBuys and the listed renovation-adjacent trades. | Keeps the first vertical slice narrow and uses the requested open source. | High | Scope or ingestion contracts need revision. | Accepted |
| R-002 | Use Postgres row-level security in addition to application organization scoping. | Tenant isolation is a data-layer requirement, not a UI convention. | High | Cross-company cost or estimate exposure. | Required before production |
| R-003 | Auth is an adapter boundary around a standard provider; no hand-rolled password or token logic. | Reduces security and compliance risk. | High | Auth integration and route guards need replacement. | Pending provider decision |
| R-004 | The Phase 0 UI uses clearly labeled empty states and no fabricated tender or financial data. | Prevents demo values being mistaken for real estimates. | High | Users could infer unsupported financial conclusions. | Accepted |
| R-005 | All monetary values will be stored as integer minor units with explicit currency and rounding rules. | Avoids floating-point drift in estimates and reports. | High | Reconciliation and audit trails become unreliable. | Required in Phase 2 |
| R-006 | French-only tender records are valid records, not incomplete English records. | SEAO and some federal records may not provide English fallbacks. | High | Search, display, and normalization could discard valid opportunities. | Required in Phase 1 |
| R-007 | Initial trade taxonomy is a seed vocabulary, not a final ontology. | Similar renovation trades overlap and need customer validation. | Medium | Matching precision and profile UX may need redesign. | Needs validation before Phase 3 |
| R-008 | RLS is forced on tenant tables; privileged provisioning must use a narrowly scoped server-side migration/service role. | PostgreSQL table owners can otherwise bypass ordinary RLS policies. | High | A misconfigured runtime role could expose cross-tenant records. | Accepted |
| R-009 | CanadaBuys closing timestamps without an offset are interpreted as UTC−0500, per the official dataset support documentation. | A server-local timezone must never move a bid deadline. | High | Closing-date filters and alerts could be wrong by hours. | Accepted |
| R-010 | The dataset URL is configuration, while the normalizer accepts documented current headers plus compatibility aliases. | Open Government resource URLs and field labels can change between dataset generations. | Medium | Polling could fail or silently lose fields after a source revision. | Monitor with schema/header alerts |
| R-011 | Dependency audit initially reported framework/transitive advisories. | The automated worker needs reproducible dependencies, but forced upgrades can introduce breaking changes. | High | A vulnerable transitive package could affect the build/runtime. | Remediated with Next 15.5.21 and patched overrides; audit clean |
| R-012 | CanadaBuys requires a descriptive User-Agent for automated CSV downloads. | The official URL returns 403 to a bare Node fetch but succeeds with an identified client. | High | Scheduled ingestion would fail despite a valid source URL. | Accepted and covered by runner |
| R-013 | Markup is modeled as a percentage of direct cost; all monetary arithmetic uses integer CAD cents and rounds line amounts to the nearest cent. | The product requires deterministic, auditable calculations, while “markup/margin” wording can otherwise be ambiguous. | High | Prices could differ from estimator expectations or be mathematically unreconcilable. | Accepted for Phase 2; validate terminology in UX |
| R-014 | Initial match weights are trade 40, certification 10, region 15, bonding 15, capacity 10, with explicit unknown-data partial credit. | Matching needs a deterministic baseline before customer calibration. | Medium | Match ranking may need recalibration after real estimator feedback. | Accepted for Phase 3 calibration |
| R-015 | Monthly finance rows use integer cents, billing minus cost for net cashflow, and null margin when billing is zero. | A zero-billing month must not create a misleading percentage. | High | Portfolio reporting could show mathematically invalid margins. | Accepted |
| R-016 | Email alerts remain disabled by default and require an explicit organization preference. | Notification delivery is an external side effect and must be opt-in. | High | Companies could receive unintended messages or incur provider costs. | Accepted |
| R-017 | Supabase security advisor identified RLS disabled on `trade_catalog`, `tenders`, and `ingestion_runs`. | These tables are in exposed `public`; tender/raw ingestion data must not be anonymously writable/readable. | Critical | Cross-tenant or operational data exposure through the Data API. | Resolved: RLS and explicit policies applied |
| R-018 | Organization membership lookup uses a server-only Supabase secret key after validating the user's signed claims. | Current RLS policies use a backend organization setting and are not yet directly compatible with browser Data API reads. | High | Exposing the secret key or using the browser client for membership lookup would break tenant isolation. | Server-only boundary implemented |
| R-019 | The previously configured Supabase project ref belongs to an unrelated Newspaper Prediction application, not BidPilot. | Applying BidPilot migrations there would alter unrelated production data. | Critical | Wrong-schema production mutation and data integrity risk. | Resolved: dedicated BidPilot project `uenlzatwyhvnccvtlmor` created |
| R-020 | Tender and ingestion-run records are backend-only; RLS deny policies explicitly block direct Data API access. | Tender raw payloads can contain source contact data, and ingestion logs are operational telemetry. | High | Public API exposure could leak contact or operational information. | Accepted and enforced in migration 0009 |
